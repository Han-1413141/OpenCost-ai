# 多订阅组合与请求分配

日期：2026-10-15。输入 `quota-portfolio-1`，结果 `quota-portfolio-result-1`，搜索方法 `quota-portfolio-enumeration-1`，回放方法 `quota-replay-method-2`。对应 Q-09 的有限目录、共同执行配置下的组合比较。

## 已实现的使用方式

网页和桌面共用“本地额度回放”面板，默认关闭。点击开启后可以选择多订阅 JSON，或查看明确情景示例；选择文件只返回概览，点击计算才搜索和回放。保留费用、覆盖、总等待、最长等待、预算和等待上限设置，编辑条件会清除旧结果。

```text
npm run contribute -- quota-portfolio-template --out NEW-portfolio.json
npm run contribute -- quota-portfolio --input portfolio.json --out NEW-result.json --enabled
npm run contribute -- schema --format quota-portfolio --out NEW-schema.json
```

CLI 未显式启用时不读取输入、身份、监控库或账户。所有输出只写新文件，保留旧输入与报告。页面清空、取消和关闭沿用短期 Worker 的终止机制，不新增后台采集、网络请求、模型调用、上传或轮询。

## 真实业务对象怎样登记

`execution` 固定模型、版本、Harness、环境和配置；`meters`、`requests` 固定同一份需求、顺序、截止条件、持续时间和必需标记。每项订阅另行声明是否支持此配置；不同模型不能靠一个价格字段混为同一资源需求。术语见 [领域定义](../CONTEXT.md)。

| 对象 | 输入内容 | 一次组合中的不变量 |
| --- | --- | --- |
| 可选订阅 | 订阅身份、套餐与版本、资格、配置匹配、依赖、互斥组、费用/池/事件引用、计量换算 | 同一订阅身份最多一种方案；加购依赖主套餐；不同独立订阅可共存 |
| 费用项目 | 整期费用、窗口付款、现金调整、完整度和当时价格记录 | 按唯一费用引用取并集；共享费用不重复，加购和闲置费用不丢弃 |
| 全局额度池 | 一份物理计数器的期初状态、规则和单位 | 选中多项共用订阅时只初始化一次；独立池分别计算 |
| 全局事件 | 赠额、重置、退回或期初占用释放 | 只加入选中订阅引用的事件；共享引用只应用一次 |
| 额度批次 | 唯一引用、数量、有效期、优先级及适用范围 | 输入禁止同一批次复制到不同池或事件 |
| 分配组 | 请求引用及明确允许的订阅引用 | 每个请求恰好属于一组；一组内全部请求使用同一订阅 |
| 必需购买 | 已买或其他原因必须保留的订阅引用 | 即使不分配请求也计入该订阅的完整费用与相关池 |

全局目录可以包含未选中订阅的池、事件和费用，构造时只取选中项的并集。购买时才发放的加购额度应登记为该购买引用的事件，不能预先混入所有方案可用的期初余额。一个池在不同互斥方案下有不同容量时，需要分别明确建模，不能把两个互斥容量相加。

现有回放内核支持一份明确的超额计费规则。多种不同超额单价、分段计费或动态优惠尚未统一支持。`overageCoverage` 必须声明完整、部分或未知；部分和未知停止完整比较。不能遗漏另一项订阅的超额规则，再用已填写的一份单价宣称全部费用完整。供应商页面、用户输入及文件导出只是来源声明，未联网核验。

## 算法

先枚举最多 8 项目录订阅的非空子集，共不超过 255 个购买集合。过滤超过同时购买数、缺少必需购买、依赖不满足、互斥冲突、重复订阅身份或不能为某个分配组选出订阅的集合。资格和配置是否适用在结果中另行保留为已排除或未评估。

对每个结构允许的购买集合 S，令每个分配组的可选订阅为：

```text
该组允许的订阅 ∩ S
```

该集合的分配组合数是各组选择数的乘积。全部购买集合的组合数相加得到搜索规模。使用 BigInt 精确计数，并以十进制字符串保存；不先建立指数大小的数组。例：两个独立订阅、2,000 个均可二选一的请求组，其分配空间包含 2^2000 个双订阅路线，不会按普通 Number 近似。

超过用户选择的分配预算时，预检直接返回容量状态和未处理数量，不运行一个有利前缀。规模在预算内时用混合进制索引迭代全部分配，不递归建立搜索树。一个组只给一项订阅，就表示明确固定分配；多个请求可以放进同一组，因此大量已知路线不必按每条请求再展开全部替代项。

对每个分配组合：

1. 按唯一引用合并费用、物理池和被选中的事件。
2. 按每个请求所属订阅的计量绑定，以 BigInt 逐请求向上取整换算需求。
3. 保留原始到达、同刻顺序和截止条件，在同一份池状态上运行所有请求；每池 FIFO 和多池原子扣除沿用原回放规则。
4. 资格、配置、换算、来源覆盖或规则未知时保留原因；不通过减少池或把未知量补零继续计算。
5. 只在整个相同必需集合已安排时计算必需总等待和最长等待。费用、预算与等待条件复用单套餐比较的同一函数。
6. 在满足偏好且指标已知的分配中比较用户选择的主目标，保留所有精确并列。费用未知时不能参加费用优先；无预算的等待优先可以保留未知价格。

一个方案安排更多请求不等于完成更多任务，等待未覆盖请求不计为零。同一根目标的工作量不会因使用两个订阅或多个池而增加。

本地方法参考 [OR-Tools 官方求解状态](https://developers.google.com/optimization/cp/cp_solver) 对“找到可行方案”和“证明最优”的区分。这里使用现有 TypeScript 回放器及有界穷举，没有安装或调用 OR-Tools；也没有使用 `cumcm-statistics`。完整穷举只说明当前明确目录、规则和允许分配内完成比较；未知费用与资格仍使相应选择不可判定。

## 资源与历史

输入最多 2 MiB、8 项订阅、32 个费用项目、2,000 个请求、32 个全局池、2,000 个全局额度事件；最多 256 个分配评估，最多 100 万总回放步。每次回放继续使用原 20 万步及规则条目限制。整体最多 10 万构造额度引用及 10 万保存的分配引用，未知资格也不能绕过后者大量保存组合。

任何中途容量耗尽，清除整份候选数值、选择和选中回放，保留实际已处理数、步骤、未处理数及本次输入。不用先完成的廉价方案形成赢家。额度与分配引用最多可在最后一次构造时越过阈值一个有界候选，该阈值不是进程 RSS 硬上限或生产吞吐量证明。

报告保存完整输入、当时价格时间和来源、规则版本、每个组的订阅分配、唯一费用与池引用、方法版本和计算时间；精确并列的较优分配保留完整回放。旧结果不随新价格或新方法重写。当前价格、实际购买、自动读取监控历史和公共排名均不由这个本地情景结果更新。

## 界面和验证

组合列表每页 20 项；较优分配的组列表每页 50 组，额度回放每次只展示一份，避免把所有请求与并列方案同时绘制。界面显示当时价格、完整购买费用与窗口现金、覆盖、等待、搜索范围、未知原因和具体分配。完整内容可保存 JSON 复核。

验证包括共享物理池和赠额不翻倍、费用并集、同一订阅身份互斥、加购依赖、重置等待、闲置费用、未知资格与价格、精确舍入、输入顺序和多种整体容量。36 个简单余额情景以独立枚举公式对照；另有明确分配的 2,000 请求情景。CLI、打包 Worker、共享界面静态渲染及原比较功能分别检查，最终数量与构建目录见 `docs/status.md`。

仍未实现跨模型工作需求预测、全市场目录搜索、多份不同超额价的统一联合计费、未来不确定需求、供应商真实资格校验，以及真实 GUI 和新机器安装验收。自动功能与难度分级继续默认关闭。
