# 本地额度观测导入

实现日期：2026-10-15。输入 `quota-observation-import-1`；输出 `quota-observation-import-result-1`。对应清单 Q-07 的文件适配、核对和共享界面部分。

该功能把用户选定的原始额度观察与明确映射转换成 `quota-replay-1` 情景。程序先检查覆盖、规则、引用及数量，再按实际扣除时点核对一遍账目，只有通过后才返回可运行输入。调度情景由用户另行运行。后续已接入 [监控历史只读导出](monitor-history-export.md) 和 [有限目录多订阅比较](quota-portfolio.md)；供应商自动规则适配、请求历史自动补录和定时自动导出仍待做。

## 使用

网页和应用使用同一“本地共享额度回放”面板。默认关闭；开启后选择情景或观测JSON。观测导入展示时段、观察/池/请求/事件数量、假设和缺口。核对通过后可保存转换情景，再点击“计算共享额度与费用”。换文件、关闭、取消或离开页面会使旧读取与Worker结果失效。原始观察不回传到界面结果，也不上传。

CLI示例：

```text
npm run contribute -- quota-observation-template --out NEW-observations.json
npm run contribute -- quota-observation-import --input selected.json --out NEW-check.json --scenario-out NEW-scenario.json --enabled
npm run contribute -- quota-replay --input NEW-scenario.json --out NEW-replay.json --enabled
npm run contribute -- schema --format quota-observation-import --out NEW-schema.json
```

转换命令默认关闭，未带 `--enabled` 时不读取输入、身份、状态文件或监控库。它只保存关闭报告；模板与Schema生成也不读取用户历史。所有新转换输出必须使用不同的新文件名。资料不完整时只保存核对报告，不创建可运行的部分情景。模板为固定合成示例，转换后继续保留 `explicit_scenario`，不作为真实历史。

JSON Schema提供字段类型、枚举和容量；引用、守恒、时间语义及跨记录关系还必须通过转换器检查，不能只凭Schema声称可以回放。

## 输入字段

| 字段                               | 内容与作用                                                                           |
| ---------------------------------- | ------------------------------------------------------------------------------------ |
| `importRef/subscriptionRef/window` | 本地随机引用、单个订阅、用户选定绝对起止时间                                         |
| `observations`                     | 原 `SubscriptionSnapshot[]`，保留原观察和流水；不包含账号、密钥、URL或任务正文       |
| `mapping.scenario`                 | 完整候选 `quota-replay-1`，包括规则、期初批次/占用、请求、边界事件和明确费用情景     |
| `mapping.claims`                   | 请求及共享账户覆盖、需求完整性、规则/顺序/资格依据、费用是否仅为用户情景             |
| `mapping.pools`                    | 每池期初与期末观察引用、状态实际时刻、时间依据和流水数量含义                         |
| `mapping.requests`                 | 请求到达时间与依据、是否实际消耗、实际扣除时间/顺序、同请求在各池的原始usage事件引用 |
| `mapping.events`                   | grant/reset/额度退回与原始流水的对应                                                 |
| `mapping.expirations`              | 到期流水对应的额度批次                                                               |
| `mapping.recoveries`               | 自动恢复/并发释放对应的初始占用或请求引用；原流水使用refund时明确表示额度恢复        |

`mapping=null`可保留原观察并获取缺口报告。不会通过两次余额差生成请求、推断重置或补全任务引用。DSH目前只有百分比、单位和绝对容量未知的观察会提示资料不完整。

完整的额度流水不等于完整请求历史：未消耗请求、被拒绝请求也要在需求列表与请求覆盖说明中保留。`not_consumed`请求没有扣除引用，仍出现在最终需求情景里；记账核对不为它制造消费。一个已消耗请求在全部涉及池中只能登记一次需求，必须明确原子扣除的时间；各池不同时间扣除尚不能等价为现有原子需求。

## 时间边界

输入时间必须能准确表达为毫秒。高于毫秒的时间不静默截断；观察时间不自动当作到达、扣除或状态时间。状态时刻不能晚于观察时间。

外部请求及重置、赠额、退回采用 `[startAt,endAt)`。源额度流水是 `(from,through]`，故完整覆盖要求首段从start之前开始，并连续覆盖到end；请求覆盖区间则按声明的闭合端点连续合并。分段之间有间隙，不用最早/最晚时间掩盖。

期初和期末状态边界统一声明为 `after_automatic_before_external`：该时刻的半开到期和自动释放已经生效，该时刻的外部操作还未执行。期末同刻的外部重置不纳入；同刻的到期或自动恢复影响期末余额。这个定义与现有回放引擎一致，不移动任何事件一毫秒来修正顺序。不能提供此边界状态时，应保留缺口或明确时间假设。

到达与扣除分别存储。核对账目使用原扣除时刻，且每次扣除必须在该时刻可安排；最终情景使用原请求到达时刻，因此保留原来等待的事实，同时可以模拟固定队列规则下的不同等待。它不宣称重现供应商真实调度器。

## 引用、数量与守恒

- 按 `(subscriptionRef,poolRef,eventRef)`合并一致重复；相同标识不同内容是冲突。两个都声明完整的重叠流水还须互相包含区间内已知事件，不能取并集后掩盖一方缺漏。
- 选中观察中的所有额度池都必须有规则和映射。不删除未知池，不把局部Harness数据称为全部共享消费。
- 要求准确绝对余额、单位、有限整数容量和规则版本；不把百分比乘以假设容量，不舍入小数。当前回放整数初始状态和数量限制继续适用；动态/无限、存储占用及缺规则类型返回缺口。
- 余额、明确固定窗口、滚动、并发和连续补充复用现有引擎。滚动初始消费时间、并发释放时刻和连续补充速率必须明确。缺时长、资格、类别或初始历史不当作真实冲突。
- usage原数量与该请求的全部池需求对应；重置数量表示新发额度，不是净余额差；赠额表示发放量；refund明确为额度退回或自动恢复，不能把现金退款套入。
- 每个源事件只能被核对一次。没有映射的源事件、规则产生但流水未记录的正数量事件、数量/时间不同、扣除不可满足或末余额不同，都阻止生成完整输入。
- 到期、重置后批次不因退回复活。自动恢复只恢复尚占用部分，不形成负消费。原始counter信息存在时，同一usage前后已用差还要与该事件数量一致。

对于恢复或到期实际为零的情况，源可以不记录零数量事件；已有零数量映射仍须能重现。原始观察不改写，不增加一笔correction凑平账目，未知语义的correction保留未映射缺口。

## 费用和来源声明

`claims.cost=unknown`时，转换输入的完整周期费用、窗口费用均为null，现金调整为空、超额价格为空。不会把快照 advertised/billed价格当作已核对付款，不乘席位、按天均摊或填零。若选择付费补足却缺规则，直接提示缺口。

`claims.cost=explicit_scenario`保留用户给定的费用规则，并将整个需求基础标为明确情景。规则、状态时刻、到达时间或资格采用假设时同样标为情景，并在报告展示假设。只有这些信息均声明为来源事实/本地记录且原输入不是情景时，才使用 `observed_demand`。这表示需求记录的声明性质，不证明来源可信、规则真实或模型任务通过。

## 输出、资源及边界

输出为disabled、ready、incomplete、conflict或capacity。只有ready保留 `input`。其他状态不包含可运行前缀；诊断用固定代码和本地随机引用，不回显原文、供应商异常、账号或文件路径。网页最多展开30项，完整报告最多100项诊断，超出转为capacity。

上限：2MiB输入、1024份观察、8000个窗口内唯一源事件、16000个源引用，沿用回放2000请求/2000外部事件/32池及200000步。观察上限由原256调整，用于覆盖默认5分钟一次、近3天约865份观察；字节和源事件约束未放宽。区间端点预先解析，诊断达到容量后结束。记账轨迹只在转换时通过可选回调产生，最多保留16000个核对引用，不出现在公共回放结果中。默认回放未配置回调，其结果和行为保持原协议。

每次手动导入只执行一遍记账核对；运行情景时使用转换文本，不重新读取原观察或再次核对。短生命周期Worker执行并支持取消，没有新增轮询、网络请求、数据库读取、上传和模型调用。此边界不是正式线上吞吐量测量。

程序验证结构、已知记录和声明之间是否一致；随机引用、Schema或数值守恒都不认证事实来源。供应商适配、账户完整范围、规则发布和实际付款来源仍需独立取得。该功能不进入生产难度分级或公共排名。

实施前方案见 [Q-07设计](quota-observation-import-design.md)，其中未实施描述保留为当时快照。当前监控库只读导出及有限候选/组合已按各自文档接入；定时自动导出、历史事件自动补录和需求预测仍未完成。
