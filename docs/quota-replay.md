# 本地共享额度与费用回放

版本：`quota-replay-1`；结果：`quota-replay-result-1`；当前计算方法 `quota-replay-method-2`。这是显式单方案的本地计算入口，默认关闭。它没有账户查询、模型调用、上传或公共排名写入。所有时点相对于情景开始，单位为整数毫秒。新结果记录计算方法；旧结果缺字段保留历史状态，不补写数值。

网页“我的记录”和桌面“反馈”提供相同面板。点击“开启本地额度回放”，选择最多 2 MiB 的 JSON 后只检查规则；点击“计算”才运行。计算使用短期 Worker，完成、取消、关闭和页面卸载都会终止。输入与结果只保留在当前页面内，用户可手动保存 JSON。示例明确标为情景；显示获准请求，不将其换算为验收任务。

## CLI

```powershell
# 新文件，不覆盖已有情景
npm run contribute -- quota-replay-template --out .local/NEW-scenario.json
# 默认关闭；不读取 --input，亦不读取身份或采集状态
npm run contribute -- quota-replay --input .local/scenario.json --out .local/NEW-disabled.json
# 用户选择启用后才读取指定情景
npm run contribute -- quota-replay --enabled --input .local/scenario.json --out .local/NEW-result.json
```

输出文件采用独占创建。输入原文、路径、JSON 异常详情不会写入错误说明。协议以 `shared/quota-replay-schema.ts` 为准；导出的情景文件是本地文件，不是贡献上传格式，也不代表真实账单或任务成绩。

## 数据和未知条件

每个方案、池与请求有稳定的本地情景引用。输入明确套餐资格、外部共享消费是否包含、需求是否列出全部必需限制、同刻来源或情景序号。未知单位、需求、滚动历史、并发持续时间、赠额资格或必需规则使整份情景返回 `not_evaluated`；未知固定付款仅使对应费用未知，额度可以独立算完。

当前不把 `shared/subscriptions.ts` 的快照自动转换成回放。快照余额不包含滚动消费的恢复时间，也不保证能解释赠额批次、外部消费和退款。`observed_demand` 表示输入声明来自观察需求，调度仍为规则情景，不证明未来任务效果。

## 支持的池

| 池           | 必需状态                                     | 时间处理                                                |
| ------------ | -------------------------------------------- | ------------------------------------------------------- |
| balance      | 期初批次，优先级、期限、适用类别和是否可重置 | 消耗按优先级、到期、发放顺序；固定窗口用明确 reset 事件 |
| rolling      | 容量、窗口长度，期初窗口内逐笔消费时间       | 每笔在原消费时间加窗口长度恢复                          |
| concurrency  | 容量、期初占用结束时点，请求持续时间         | 每笔独立结束；零时长不留下占用                          |
| token_bucket | 容量、初值及每段时间补充量                   | 有理数 BigInt 精确推进，达到容量即停止累积信用          |
| unsupported  | 未支持原因                                   | 动态容量、存储占用或未知政策等不忽略                    |

连续补充的剩余显示量为浮点近似，结果同时保留 `remainingExact` 的整数分子和分母。容量判断和唤醒计算使用 BigInt，不依据界面四舍五入后的值。

额度有效区间是左闭右开：到期时不能再消费；滚动与并发恢复以及到期都在同刻有序操作之前处理。外部 grant、reset、return 和请求到达采用输入序号。同刻没有可靠顺序且可能影响结果时不猜测。`latestStartMs` 包含该时点，但情景结束时点不再安排新请求。这是开始截止，不是完成截止。

请求必须在所有依赖池同时满足，并在各池按共同到达顺序排到队首才扣除；独立池仍可以继续。失败不提前扣任何池，也不计超额费用。需求超过不会变化的硬容量时立即标为未覆盖，让可行后续请求继续；余额池的未来赠额可能改变可用量，因此不能同样判定。

## 事件、退回和费用

- 相同 ID、相同内容的额度/现金事件去重；相同 ID 内容不同拒绝。
- reset 明确舍弃全部或仅可重置批次，再发放新批次。余额 20 重置到容量 100 不是增加到 120。
- 额度退回引用本情景中已经获准请求的原批次扣除，累计不能超过原扣除。重置或到期后的批次不复活，单列退回失效。
- 滚动退回引用原占用，累计不得超过原消费；自然释放只恢复剩余占用，避免重复恢复。已自然恢复后的退回不再次增加额度。
- 现金退款与额度退回独立。输入内的现金调整属于整段已声明情景，不是程序已观测到的真实现金流。
- 完整购买周期固定费用只计一次并包含闲置；窗口内固定现金另列。模拟开始前已购买不代表完整方案费用为零。
- 只支持一条绑定余额池、资格明确的线性超额规则；支持每请求向上取整或全期累计后向上取整。付费不能购买速率或并发限制，也不自动推导阶梯、税费、币种转换等规则。
- 窗口现金可以因退款为负；完整成本为负或超过计算范围时不用于费用比较。缺固定费用不自动补零。

## 输出与资源约束

状态为 complete、not_evaluated、incomplete 或 conflict。分别输出请求获准、未覆盖、未知，开始/声明服务结束、等待与等待下界；根目标只按引用去重，不视为已完成工作。统计的最长等待只属于已获准请求，没有获准请求时为未知。处理中断或冲突时 `currentTimestampComplete=false`，该时点可能只处理了部分事件；余额、占用及完整费用保留未知，累计已处理事实仍保存。

每池保留请求总需求、剩余、发放、到期未用、重置舍弃、滚动恢复、退回/失效、占用和超额补足。请求总需求是累计获准需求，退回不把历史需求抹掉；它不是净余额扣除。滚动自然恢复不是浪费。冲突或处理预算到达时保留已经处理的前缀，完整超额及整期费用不输出。

输入上限为 2 MiB、2000 请求、32 池、2000 外部事件、4000 期初/发放条目、16000 需求引用、366 天。处理逻辑有 200000 步预算，超出不静默截断。内部最小堆按边界和恢复推进，不逐毫秒轮询，不重新扫描全部历史占用。批次匹配可能随可用批次数增长，复杂匹配达到预算后返回未处理范围；预算不是已验证的生产吞吐量。

## 与套餐推荐的边界

现已提供 [本地观测文件与映射导入](quota-observation-import.md)，只转换记录完整且核对通过的输入；另有[有限候选套餐比较](quota-plan-comparison.md)，固定共同配置和需求，保存候选集合及规则版本。没有自动读取监控库或用余额差补造历史。多套餐联合购买/分配搜索、用量预测、模型成功率预测、真实规则目录或主榜接线仍未实现。更换模型后同一任务的Token和耗时可能变化，不能直接把当前模型用量当另一模型真实需求。比较只称“已评估且满足偏好候选中的较优方案”。

方法依据来自本项目已阅读的三份 Pro 资料和 [采用记录](research/pro-reference-adoption-20261014.md)。事件调度、队列和令牌桶是通用建模方法；供应商实际条款仍须独立确认。当前用例为合成数据，验证程序行为，不证明真实供应商套餐或模型任务效果。
