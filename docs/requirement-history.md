# 要求历史、验收与任务重开

日期：2026-10-15。对应清单 L-02、L-05、L-07、L-09、L-10 与 F-01 的部分工作。源码已经接入本地分析、capture、上传校验、公共当前资格及私人反馈；实际构建和运行状态见 [项目状态](status.md)。功能不自动启用，不调用模型。

## 统计含义

根目标由用户原始独立验收目标确定。原要求版本、变更提案、用户批准、成果检查、结束及重开分别记录；多次验收、重开或多个代理不增加根目标。

“原要求曾验收”描述已发生的事件；“当前原要求通过核对”描述当前成果所支持的事实。验收后发现问题再重开时，前者保留，后者在新核对之前未知。当前进行中、暂停、等待用户、等待外部、受阻或等待验收都不是最终失败。明确结束后的失败保留最终结果及原因，不因曾经验收而删掉失败费用。

要求删减只有真实用户事件或明确人工报告的批准才生效；模型自报批准仍只是待确认提案。当前范围全部通过不自动证明原要求通过。模型自报检查结果可以留在本地，但不能建立用户/验证器验收。来源字段是输入声明，不认证用户身份或验证器。

## 本地协议

输入格式 `opencost-local-task-history-1`，分析报告 `opencost-task-history-analysis-1`，方法 `requirement-history-method-1`。每个事件包含随机根目标 ID、事件 UUID、明确父事件、发生时间和本地记录时间。允许下列事件：

| kind       | 含义                   | 必须满足的关系                                                   |
| ---------- | ---------------------- | ---------------------------------------------------------------- |
| baseline   | 原要求及必需条件       | 每根恰好一份起点，父事件为空                                     |
| proposal   | 提议改变范围           | 期望要求版本须仍有效，新要求引用未被使用                         |
| decision   | 批准或拒绝提案         | 明确引用已有提案，不能重复解决；批准需用户事件/人工报告          |
| assessment | 当前成果版本的逐项检查 | 条件及定义引用属于当前要求；一次检查作为完整快照，不混拼不同成果 |
| state      | 非终态阶段及原因       | 当前要求有效；已经结束须先显式重开                               |
| closed     | 最终验收、失败或取消   | 验收要求非空且全部必需项已由用户/验证器检查通过                  |
| reopened   | 重开同一要求           | 引用当前准确的结束事件，清空旧成果检查，保留原验收历史           |

批准新要求会清空旧检查；验收后批准新范围是范围变化，不自动算原交付缺陷重开。条件数、条件引用和定义引用属于本地材料；协议不要求也不上传条件原文。

分析按照 `recordedAtOrBefore` 截止选择已知事件，再沿父关系重放。发生与记录时间使用 UTC，最多毫秒精度；父子时间不能倒退。后来记录不倒灌旧报告。现阶段不自动合并迟到的旧核验、并发分支或任意历史改写；事实修正须保留原输入，使用明确修订流程。

同事件相同内容在容量内幂等；同 ID 不同内容、缺父、跨根引用、循环、分叉和脱离主路径均产生冲突。输入数组顺序不选择赢家。冲突、非法或容量超限时整个报告无可上传任务前缀。

容量为 4 MiB JSON、10,000 个事件、500 个根目标、每事件 100 个条件/结果、累计 100,000 个检查引用。限额是本地工作边界，超出后要求拆分明确范围，不截断后称全量完整。

## 上传字段与入口

```text
npm run contribute -- task-history-template --out NEW-history-example.json
npm run contribute -- schema --format task-history --out NEW-history-schema.json
npm run contribute -- task-history-analyze --input selected-history.json --out NEW-history-report.json --enabled
npm run contribute -- capture --input selected-capture.json --out NEW-record.json
```

模板是方法示例，不能当真实事件。分析未启用时不读取输入文件，也不访问身份、历史或数据库。给用户选择的本地 capture 添加 `taskHistory` 后，编译器运行同一分析器；根目标集合必须与 envelope.tasks 一致，不能漏选或偷偷扩充范围。

只有 `task.observations.history` 投影随正常预览与上传流程发出：

- `observed`：本次提供的事件、提案、批准变化、重开及验收小计。
- `baselineRequired/currentRequired/currentPassed`：原要求和当前必需项数及当前通过项数。
- `approvedChanges/pendingProposals/reopenedCount/acceptanceEvents`：完整历史确认的累计数。
- `originalAcceptedHistorically/originalVerifiedNow/activeReopen`：历史验收、当前核对和活动重开状态。
- `phase/currentOutcome/reason`：执行阶段、最终结果和原因。
- 固定版本及 `meta.source/coverage/timing/missingReason`。

不上传条件/定义/成果/事件引用、父事件、逐项结果、发生时间、记录时间、日志、路径或原文哈希。根目标仍使用既有随机任务 ID。局部或未知覆盖只保留已提供事件小计；全量次数、验收判断与当前状态未知。未测量不是零，source/coverage 未知不能携带完整已知结论。

投影与原验收项数、通过数、进度、终态或要求锁定矛盾时拒绝生成记录，不静默重写这些字段。旧记录未提供 history 时沿用原资格，缺字段不证明从未发生变更。

## 跨记录结算与排名

单条记录出现批准范围变化、尚未结束的重开或历史未知时，不作同一原要求的完整结算比较。当前成果、历史验收和费用仍保留，新增事件不被当作完成目标。

当前公开资格还检查同持有人、同根目标的有效要求历史。即使重开记录是私人记录、费用不完整或没有资格上榜，也暂停相交旧结算；不同持有人、合成或已隔离记录不产生该阻断。公共查询只处理内部随机引用，不公开私人任务、金额、次数或原因。该规则在全量条件、证据或月份筛选之前生效。

没有明确替代关系的重开不会被更晚上传、较大修订号或另一条终态自动清除。同一原要求使用 `settlement-revision-1` 的明确整条累计快照修订；合法新终态替代重开版本后，重新检查完整费用与其他比较条件，所有尝试费用仍包含在累计数中，不把多次完整快照相加。历史验收事件数也不作为新目标数。

私人反馈按自身接收序号/时间截止读取本人历史；后来重开不改写当时冻结报告。当前读到先前尚未解决的相交历史时，停止单位成本参照和推荐，并显示历史待明确，而非虚构为最终失败。

跨要求版本结算链、跨期退款差额、多父经济包含图、多条修订链合并和跨设备身份合并仍未实现；不能通过放宽旧结算要求检查代替这些功能。

## 数据库与性能

公共事实编译器升级为 `public-facts-11`，触发器版本 5；新编译器身份使旧当前统计失效，沿既有 128 条/2 MiB、首条 4 MiB 的有界准备流程重建。历史反馈文件不改写。

新 `requirement_history` 标记在贡献写入时由 SQLite 的 JSON 解析器产生，处理转义字段名，不用字符串搜索猜测字段。首次引入该协议前，合法旧记录不含这个扩展，因此旧标记默认零；不扫描所有私人旧正文。普通私人记录仍不加入公开事实队列；主动提供此扩展的私人记录进入内部当前资格判断，公开输出继续由原同意控制。标记和索引属于可重建元数据，不是新工作量证据。

内部 `public_fact_history_blocks` 按持有人和根目标建索引；当前资格排除尚未被有效修订替代的阻断。私人生命周期投影版本 2 保存完整结算根和要求历史阻断，旧 valid 行也须按新版游标有界重建，不因旧状态跳过检查。正常写入仍使用原事务、预算和变更队列，不增加轮询、模型请求、账号查询、自动上传或后台扫描。

## 研究采用范围与验证

采用 [Martin Fowler 的 Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html) 中用事件保留变化及重建状态的设计；采用 [Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html) 对事实时间和记录时间的区分。这里实现的是有界单父事件链与接收截止投影，未实现通用双时间数据库或任意追溯修正；两篇资料不提供本项目评分准确率的证明。

验证覆盖事件幂等/分叉/断边、用户批准、模型自报、要求缩减、成果检查隔离、原验收与重开共存、最终失败、局部未知、上传脱敏、跨记录私人阻断、当前修订恢复、接收截止及旧投影重建。测试使用明确的隔离合成记录，不向真实服务上传。运行次数和最终构建见项目状态。
