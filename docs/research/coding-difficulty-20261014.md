# 编程任务难度：论文核对与 OpenCost 采用范围

核对日期：2026-10-14。本文根据用户补充的文献清单读取论文方法、结果及项目说明，记录可以迁移的方法和当前实现。没有复现外部论文的训练结果，没有运行其模型文件，也没有把外部精度写成 OpenCost 的精度。生产难度分级继续默认关闭。

## 2. 三个层次各自回答什么

### 执行前：要求与已有环境

记录原要求的组成、约束、方法类别、依赖关系，以及授权范围内原有代码的结构统计。程序适合数分支、函数、参数、依赖和分散度；需求是否含糊、是否需要原创证明等语义判断，可以由用户或模型按封闭规则提供，但必须标明来源和未知项。

这些是难度预测的候选特征，不是已校准的难度。任务换了要求、验收条件或资源协议，应当保留新的版本，不能只追加结果。

### 执行后：实际交付与资源

记录验收、修改规模、补丁分散度、代码结构变化、全部尝试的 Token 和成本。必须区分候选补丁、已验收补丁、基准标准答案，不能互相替代。修改后的复杂度受代理行为影响：多写代码、多次返工都不能让任务自动升值。

任务仍在进行、等待用户、等待外部条件或等待验收时，记录进度和已发生成本；只有明确结束才能进入最终完成结果统计。当前实现已增加该区分，不会把一天的采集截止当作失败。

### 有共同任务以后：经验难度

同一任务版本在不同完整配置中执行，保留成败、试验数、资源条件和验证器版本。用这些记录估相对难度；按任务族、仓库和时间留出，验证新任务上的预测。来自同一需求的重试不能分到训练和测试两边。

不能仅凭相似的脱敏摘要就断言是同一个锚点任务。公开基准使用固定任务标识和清单；私人数据应保留本地需求版本关联，跨用户是否同题未得到证明时，不合并为共同任务。

## 3. 模型与 Harness 分解之前的程序检查

拟研究的加性关系为 `logit(p) = theta_model + theta_harness - beta_task`，现有拟合仍是 `theta_configuration - beta_task`。

两个例子说明为什么需要检查：

- 模型 A 只搭配 Harness X，模型 B 只搭配 Harness Y，即使都做同一批任务，也不能确定差异来自模型还是 Harness。
- 模型与 Harness 的搭配图连通，但某些搭配只做另一组任务，仍可能无法区分配置能力与任务难度。只数样本或检查搭配连通并不足够。

新增诊断从已观测的“模型—Harness—任务”单元构造设计矩阵，检查去掉两个平移自由度后是否满秩，同时报告缺少交叉、未观测配置和同一模型/Harness 存在多种配置版本等情况。重复同一个单元一万次只能改善该单元的估计精度，不能补出缺失的交叉关系。

满秩仅表示在加性假设下可以区分参数，不说明样本够多、没有混杂、没有模型与 Harness 交互、概率已经校准或存在因果关系。因此诊断不生成新的模型/Harness 能力分，也不改变生产榜单。

独立方法评审确认：如果完整配置—任务图和模型—Harness 图都连通，纯加性设计已满足上述结构识别条件，不能声称还存在额外的精确线性混杂。诊断保留矩阵秩是为了覆盖输入不足时的解释。另一个边界是：每个任务已有自由难度参数时，随任务固定不变的代码特征属于任务列空间，不能直接追加系数就宣称识别了其独立作用；特征预测需要独立的训练与留出步骤。

## 4. 成熟工具如何选择

当前已有 JavaScript/TypeScript/JSX/TSX 的本地 AST 结构测量，定义和限制见 [代码测量说明](../code-complexity.md)。本轮进一步核对的工具如下；尚未安装或接入这些外部项目。

| 工具                                                               | 用途与采用决定                                                                          |
| ------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| [Lizard](https://github.com/terryyin/lizard)                       | 后续多语言函数结构适配候选；保留语言、工具版本和解析覆盖率，不把不同语言的数值直接排名  |
| [Radon](https://radon.readthedocs.io/en/master/intro.html)         | Python 圈复杂度、Halstead、维护性指标候选；名称中的 Difficulty 不能替代任务难度         |
| [Complexipy](https://github.com/rohaquinlop/complexipy)            | Python 认知复杂度候选。需要固定算法版本；当前 AST 嵌套计数并未冒充该认知复杂度算法      |
| [Wily](https://github.com/tonybaloney/wily)                        | 借鉴跨 Git 版本保留测量历史。不能让用户当前文件代替历史版本；后续只测明确授权的版本范围 |
| [code-complexity](https://github.com/simonrenoult/code-complexity) | 变更频率与代码复杂度适合找维护热点；该分数不表示完成任务数量，不进入性价比的收益分子    |

## 5. 后续字段与采用条件

以下是候选协议设计，不表示上传接口已接收或采集这些字段。保持开关关闭，先实现本地测量和结构校验，再扩展上传白名单。

| 信息         | 适合保留的脱敏量                                                                                      | 使用条件                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 采集阶段     | `before_execution / during_execution / after_execution / unknown`，原要求版本、测量方法版本、覆盖状态 | 不依据文件修改时间猜阶段；事后补录不能冒充事前证据                                            |
| 原有代码     | 按语言分开的函数/分支/嵌套分布，成功解析数、未解析数                                                  | 源码留在本地，不保留标识符和路径；没有授权或不支持语言时记未知                                |
| 实际补丁     | 文件数、连续修改块数、增删行、每文件修改量分布、测试与业务代码的声明分类                              | 阶段及补丁类型明确；不上传 Diff、文件名、提交消息、作者或邮箱；重命名/格式化/生成文件分别识别 |
| 验证条件     | 原验收项数、已检查覆盖、通过/失败/未知数量、验证器来源与版本                                          | 重复运行同一测试不增加验收项；通过自编测试不等于用户已验收                                    |
| 行为与费用   | 人类干预、澄清、返工、各层子代理调用、Token、等待与运行时间、历史价格依据                             | 缺项不填零；累计快照去重；等待时间不当作模型计算时间                                          |
| 人工时间参考 | 实测/用户估计/模型估计的来源、参考经验组、样本窗口                                                    | 任务与参考人群可比才校准；不用模型猜测冒充实际人工劳动                                        |

评价预测时同时检查 Brier score、LogLoss、概率校准、任务难度排序、关键子组误差和区间覆盖。解释特征作用时保留相关性措辞，SHAP 不能独立证明因果。缺少足够真实交叉数据时，展示结构观察和数据缺口，继续使用真实验收与费用计算性价比。

## 6. 本轮实现边界

- 已有：默认关闭的本地任务要求结构、AST 代码结构、配置级 Rasch 校准；未结束任务与最终失败区分；成本与完成率的并列解释。
- 本次补充：校准数据对模型/Harness/任务的可识别性诊断及构造反例测试；以上文献的来源、限制和迁移记录。
- 尚未实现：标准答案补丁预测器、Python/其他语言适配、因子化 IRT 拟合、人工工时预测、真实跨领域预测验证。它们不会随下载工具包自动启用。

随后增加本地 `measure-code-set`：对用户指定文件清单按语言合并结构分布，保留原要求修订、声明阶段和范围，并记录去重及测量缺项。没有将后验代码指标转为事前难度或工作量奖励；候选的上传字段仍未接入。

这些资料给出了可检验的研究路线；“有研究依据”不能写成“已经准确覆盖所有领域”。当前未声称仅凭脱敏摘要可以精确恢复原任务全部难度。
