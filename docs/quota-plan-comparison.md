# 有限候选套餐比较

日期：2026-10-15。输入 `quota-plan-comparison-1`；输出 `quota-plan-comparison-result-1`；比较方法 `quota-plan-selection-1`；回放方法 `quota-replay-method-2`。对应清单 Q-08、F-10 的费用与等待偏好部分。

在同一模型、版本、Harness及其配置下，固定一份资源需求与时间线，运行用户明确列出的有限候选。分别展示请求覆盖、完整购买费用、窗口现金和同一必需请求集合的等待。结论是“已评估且满足偏好候选中的较优方案”，不称全市场最优。

## 入口与默认行为

网页和应用的共享“本地额度回放”面板保持默认关闭。开启后可以导入比较JSON或查看明确标为情景的套餐比较示例。选择文件只检查结构；手动运行后才计算。用户可选择费用优先、总等待优先、最长等待优先，以及全部请求或已标记必需请求，输入预算和等待上限。编辑会使旧结论失效；预算和等待可以点击“应用预算与等待设置”确认，非法数值不能运行旧条件。

```text
npm run contribute -- quota-plan-template --out NEW-plans.json
npm run contribute -- quota-plan-compare --input plans.json --out NEW-comparison.json --enabled
npm run contribute -- schema --format quota-plan-comparison --out NEW-schema.json
```

CLI比较默认关闭，不带enabled不读取输入、身份或历史文件。模板、输入和旧报告不覆盖；报告保存本次完整输入与算法版本。关闭、取消、换文件和离开页面会终止短期Worker并清空状态。没有新网络、数据库读取、模型调用、监控或上传。

## 固定需求与候选规则

共同部分包括：绝对起始时间和时长、模型提供方/型号/版本、Harness及版本/环境、变体、模式、工具、推理和缓存；请求稳定引用、根目标引用、到达及同刻顺序、最晚开始、持续时间、必需标记和资源计量项。它们只声明同一执行配置的固定需求情景，不估计其他模型完成同一工作的Token或成功率。

各候选包括：候选引用、套餐及规则版本、资格、相关额度池、期初状态、事件、缺额策略、费用及完整度、价格记录时间/引用/来源，以及每池绑定的共同计量项。

同一物理需求可以同时受到日额度、月额度或并发等多个池限制。每个相关池都要绑定，不能遗漏限制后形成便宜方案；同一计量项可以绑定多个池。一个请求仍是一个请求，不能按池数增加工作量。

输入采用可复核的有理数换算：

```text
该池请求单位 = ceil(共同资源数量 × numerator / denominator)
```

以BigInt计算，明确为逐请求向上取整。已知供应商规则和显式假设分别记录；换算未知或超出当前范围的候选保留未评估。不同币种的货币资源不自动换汇，套餐费用币种必须与比较币种相同。未支持的累计舍入、分段非线性换算、不同模型需求变化应另行建模，不用一个未说明的系数替代。

## 覆盖、费用与偏好

默认要求全部共同请求在各自最晚开始时间内获得安排。用户显式选择“必需请求”时，仅把标记请求作为偏好约束；其他请求的已安排与未覆盖仍展示，不能改称已经完成工作。必需集合为空时不选择方案。

所有候选使用同一必需集合。只有整个集合都已安排，才计算该集合的总等待和最长等待；缺项时为null，不用已安排子集的小等待取代。安排请求不等于任务完成或验收。

费用比较使用覆盖工作窗口的全部必需购买承诺、税费和手续费。只有声明完整且引擎得到非负有限整期费用时才比较；包含闲置部分，不只按使用量分摊。窗口现金另列，可能因退款为负，不用它选择最便宜套餐。已购买导致窗口支付为零，不表示完整方案零成本。

- 费用优先：在满足覆盖、预算及等待上限的候选中最小化完整购买费用；费用未知不能入选。
- 等待优先：在相同必需集合完整覆盖的候选中，最小化总等待或最长等待。没有预算约束时，价格未知可参与明确的等待比较，费用仍显示未知；设了预算则必须能核对完整费用。
- 所有精确主目标并列全部保留，不用候选文件顺序或暗设第二权重选择赢家。
- 资格未知、规则未支持、费用范围不足和输入冲突分别保留原因。尚未评估候选可能更好，已得出的选择只属于可评估且满足偏好的部分。

预算按明确十进制字符串转换为整数分，等待按最多三位小数的秒转换为毫秒，不通过浮点乘法或四舍五入把错误输入变成有效门槛。空值表示不限，0表示真实零上限。

## 费用与等待的取舍

另行比较具有完整费用与回放的候选。方案A全面不差于B，必须同时满足：

1. A完整购买费用不高于B。
2. B安排的每一个请求，A也安排；不能只比较安排数量。
3. 对这些共同安排请求，A逐请求等待均不长于B。
4. 至少一项严格更好：费用更低、有额外安排的请求，或某个共同请求等待更短。

存在这种A时，B标为“存在全面较优候选”；否则保留取舍。不同覆盖集合不能只凭平均等待或覆盖率判定。未知费用候选不被判为更差，也不进入该费用取舍判断，报告列出未判断数量。

该关系采用标准Pareto支配原则，维度由本项目的固定请求集合及费用定义给出。核对的原始参考为[pymoo官方支配比较实现](https://github.com/anyoptimization/pymoo/blob/main/pymoo/util/dominator.py)及[官方多准则决策说明](https://pymoo.org/mcdm/index.html)。这里只采用逐维不差且至少一维更好的原则；不引入遗传算法、伪权重或外部优化依赖。有限候选直接完整枚举，不以随机搜索得到的子集冒充已列候选全部。

## 同截止点的回放修正

比较反例发现旧引擎把到达时刻内的来源sequence沿用为同刻截止事件的全局顺序。不同到达时间可以有同样sequence，堆顺序可能先淘汰较晚到达的请求，导致其在包含式截止点本可启动却未安排；反转导出数组也可能改变结果。

`quota-replay-method-2`在共同截止点按原到达时间和该时刻来源顺序处理。较早阻塞请求到达截止后退出，后续请求仍可在其包含式截止点安排；同刻发放和自动恢复继续先处理。新结果保存方法版本，旧结果缺字段时显示“历史结果未记录方法版本”，不补写旧数值或覆盖旧报告。

## 输入、输出与容量

输入上限2MiB、16候选、2000共同请求、32计量项。每个候选沿用32池、2000外部事件、16000需求引用和20万回放步限制；整体最多10万个构造引用、100万回放步。成本与请求逐项取舍最多约16²×2000个比较，随固定候选与请求上限有界。

整体构造超限、任一回放达到预算或整体剩余预算不足时，整份选择与取舍结果不可用，不保留先完成的便宜候选作为赢家。全部候选引用和原输入仍可保存；容量不是进程内存硬上限或已验证的生产吞吐量。

结果complete表示各候选回放与完整费用均已知；partial保留未评估或费用未知原因。capacity不作选择，invalid表示结构不符合输入协议。价格/资格声明和Schema不证明真实来源。UI只使用一次手动运行结果，不自动重算或轮询。

完整输入中保存所选候选集合、规则、价格记录时间和原需求，结果另含方法版本与计算时间。价格记录来源是输入声明，未自动在线核验；不将旧报价冒充当前促销。
