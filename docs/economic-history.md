# 本地经济事件与跨期费用

更新：2026-10-15。对应C-01/C-02/C-04/C-05及L-02/L-05的本地分析部分。默认关闭；网页和应用的“分领域工作标准”共用主动导入入口，CLI提供同一计算。没有读取账号、银行、邮箱或支付软件，没有模型请求、采集、上传或后台任务。原结算和排名资格不因此放宽。

## 分开回答两个问题

**本窗口发生了多少现金变化？** 按已结算事件的发生时刻选择付款和退款，使用左闭右开窗口[from,to)，每种币种分别相减。窗口最多90天，不能超过记录截止。窗口现金净支出可以为负，例如上个月付款100元、本窗口退回30元，本窗口净支出是-30元；它不是负任务成本。

**这些金额归属哪份工作要求？** 收费按用户明确提供的根目标、要求引用和工作月份分配，退款明确引用原收费。原收费在窗口之外仍可用于核对归属，不把退款改记为当前月份的新工作，也不把一项根目标的多个要求版本算作多个已完成任务。这里的工作月份是输入声明，不自动执行财务摊销或按现金月份推断。

现金窗口的完整性与费用归属历史的完整性分别声明。现金能核对完整，不代表任务映射完整；原收费未提供时仍可保留已知退款现金，但要求费用保持未确定。相同随机事件引用才有明确去重依据；不同引用可能来自同一笔真实付款，程序不会凭相似金额、时间或文字自动合并。

## 事件、观察与修订

输入版本opencost-local-economic-history-1，输出economic-history-analysis-1，方法economic-history-method-1。

| 字段                       | 含义                                                          |
| -------------------------- | ------------------------------------------------------------- |
| dataUse                    | user_records或明确的method_example；方法示例不能当实际账单    |
| coverage.cashWindow        | 已选现金范围的完整、部分或未知覆盖                            |
| coverage.allocationHistory | 已提供费用和要求关联历史的完整、部分或未知覆盖                |
| currencies                 | 明确的CNY、USD、EUR范围；不进行汇率换算                       |
| window                     | from、to与recordedAtOrBefore，UTC、最多毫秒精度               |
| observation.id / eventRef  | 本地随机观察ID及稳定经济事件引用，不使用供应商账号或付款单号  |
| revision / parentId        | 单父观察链，起点0且无父；后继为父修订加1                      |
| recordedAt / occurredAt    | 本地何时记录与结算实际何时发生；未结算时occurredAt为空        |
| kind                       | charge收费、refund现金退款、credit_grant非现金赠额            |
| status                     | pending、settled、failed、cancelled、unknown分别保留          |
| amountMinor / currency     | 最小货币单位的非负整数或未知；不接收估算小数金额              |
| refundOf                   | 退款关联的原收费事件引用；不是代理父子关系                    |
| source                     | 官方导出、已授权计量、人工录入或未知的声明，不等于认证        |
| allocation                 | 明确金额分配及其覆盖；按taskId、requirementRef、workMonth关联 |

按recordedAtOrBefore选取当时已记录的观察，再沿单父链确定每个事件当时有效的观察；不靠数组顺序或“最后上传”选择分支。后来确认退款到账、补充未知金额或修正任务归属时追加观察，原输入保留。原本已知的金额、币种、事件类别、退款对象或结算发生时刻不能用后继静默改写；已结算、失败或取消的状态也不能改成另一终态。

同观察相同内容幂等，UUID大小写、等价UTC时刻表示及分配数组顺序不制造第二笔费用。同ID不同内容、缺父、分叉、修订号/时序矛盾，或指向已知非收费事件的退款均报告冲突，撤去整份有效结果。未知原收费与已知矛盾不同：原收费不在所选材料中时保留现金并单列未关联退款，不猜测其归属。

每个已结算退款必须与已提供原收费的币种、时序和结算状态相符，已知退款合计不能超过已知原收费金额。明确分配的退款必须落在原收费已有的对应要求部分，累计不超过该部分。未知退款金额保留未知，不按零处理。pending、failed和cancelled不算已到账现金；赠额单列，不冲减现金或任务费用。供应商的“退款请求成功”不自动等于银行到账；本功能没有自动适配或认证供应商状态。

## 退款分配范围算法

对一项收费，总额为C，某份已分配要求金额为a。全部退款金额R已知，全部明确分配的退款合计为M，其中明确归给这份要求的退款为r。尚未确定归属的退款U=R-M，该要求尚余a'=a-r。

所有仍可行的分配下，这份已分配部分的净额范围为：

```text
下限 = max(0, a' - U)
上限 = a' - max(0, U - (C - M - a'))
```

第二项考虑其他部分还能承受多少退款，因此完整退回原收费时每份部分的净额均可确定为零，不需要猜比例。收费总额未知时不使用其他部分的容量；存在金额未知的已结算退款、历史覆盖不完整或未关联原收费的已结算退款时，净额下限为零，上限仍考虑已知退款的最少约束。不同收费的部分范围按同一明确要求相加；它依赖事件确实互不重复的输入关联，不证明真实世界不存在其他重复付款。

仅当已提供归属历史完整、实际收费金额和归属已知、退款金额已知、没有未关联退款或现金状态未知，且对应范围收敛为一点时，才给出该要求的已记录分配净额。否则保留已分配部分的范围和缺项。这不是整个任务的费用范围、统计置信区间、模型能力或性价比结论，也不证明任务已经结束或包含未来补费。

全程使用整数及BigInt核对，输出仍为可安全表示的整数最小货币单位；不靠浮点比例摊分。根目标数按明确随机任务引用去重，要求数单列；两者均不是完成量。同一要求引用不能同时属于两个根目标。

## 命令与两端使用

```text
npm run contribute -- economic-history-template --out NEW-method-example.json
npm run contribute -- schema --format economic-history --out NEW-input-schema.json
npm run contribute -- schema --format economic-history-report --out NEW-report-schema.json
npm run contribute -- economic-history-analyze --input selected-ledger.json --out NEW-report.json --enabled
```

模板明确标注method_example，只展示方法。分析不带--enabled时不读取输入、不创建访问身份；输出只写新文件，不覆盖旧报告。JSON Schema说明字段，完整父链、金额关系和时序仍由程序核对。

网页与应用共用默认关闭的“本地历史费用”入口。主动选择UTF-8 JSON后，短时Worker读取文本并计算；可取消，关闭或清空时撤去内存结果、终止Worker，并使未完成读取失效。每页16条要求费用，换页只操作本地结果；没有轮询、联网、浏览器存储或隐藏采集。关联号只用于本地识别，可以在表格对应项查看完整号。

本地输入和结果包含准确金额、时间及随机关联号，不是可直接上传的匿名摘要。它们不属于现有Envelope或capture字段，不能用正常上传接口提交；没有自动修正当前费用、任务验收、公共事实或排名。需要与线上经济修订关联时，须继续设计可验证的最小投影和修订协议，不能删掉既有要求与费用检查来代替。

## 容量、历史与支持边界

- 最多4 MiB输入、10,000条观察、50,000个费用归属引用、5,000项事件和5,000行要求费用。超限不输出前一部分金额当完整结果。
- 现金窗口最多90天；为解释退款而主动选入的原收费可以更早，不自动向外扩大采集范围。
- 输入观察数包含本次提供的材料；实际费用分析只使用记录截止以内的观察。后来增加材料可能改变输入数量诊断，不改变同一截止下的已知金额和关联结果，已有输出文件不重写。
- 金额未知、状态未知、已知零、非现金赠额分别保留；来源未知不伪装为官方账单。
- 暂不处理退款到账后的资金退回、拒付、汇率结算、利息、供应商账户内赠额使用/失效、原金额的追溯更正或多个事件链合并。额外收费可作为独立收费事件；重复或退款关系仍需明确。
- 目前是主动选取的本地分析，不读取真实金融账号、不作税务/会计合规判断；真实界面交互与新机器安装状态见status.md。

## 采用资料

采用[Martin Fowler的Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html)保留观察历史及重建状态的思路；采用[Bitemporal History](https://martinfowler.com/articles/bitemporal-history.html)区分事实发生与本地记录时刻。这里是有界单父观察链，不是通用双时间数据库或任意追溯更正系统。

[Stripe官方退款说明](https://docs.stripe.com/refunds)用于核对多次部分退款、总退款与原收费关系，以及待处理/失败/取消和资金到账的区别。它是一家供应商的工程资料，不代表所有支付系统规则，也不证明输入账单真实性；本项目没有请求Stripe API。可行范围公式来自明确金额约束的穷尽分配，不使用模型评分。
