# OpenCost 数据标准 1.1

本标准定义 OpenCost 接收和比较的工作记录。字段以 `shared/schema.ts` 为准，计算以 `shared/analysis.ts`、`shared/ranking.ts`、`shared/plans.ts` 为准。`/api/schema` 提供 JSON Schema；金额守恒、单位对应关系等跨字段规则由服务端执行。

新上传使用 `schemaVersion: '1.1'`，当前任务摘要使用 `evaluation.version: 'work-summary-1'`。难度分级关闭，程序只校验并汇总完成量、用量和费用，保留按已观察任务条件的 Harness 选择。历史 1.0 与 work-1 原记录保持可读；旧主观评价不参与当前分组。Skill 在本地从已授权原始材料提取字段，未取得的事实保留 null/unknown。

核心指标是完成一项符合约定要求的工作所需的实际费用。验收、输入材料规模、人工投入和过程事件用于说明费用对应的成果与条件。Token、文件数、代码行数均不直接作为成果价值分数。

新上传还须提供 `collectionWindow`：range、UTC startAt/endAt、本地展示 timeZone，以及 batch.id/part/total。区间为 `[startAt,endAt)`；固定范围接受 1/3/7/30/90 天，增量最多 3 天，超过则重新选择。旧记录缺少该字段仍可读取。时间窗口不改变原账期和任务生命周期；窗口内无法完整归属的费用或任务按 partial 保存，不能重复分摊整期订阅。精确采集时间仅在私有记录中保留，公开分组不提供个人时间线。

## 1. 统计单位

**任务**是一项可以独立验收的目标。多轮对话、工具调用、模型切换、返工和重试归在同一任务内。同一任务不能拆成多份成功记录；只选父任务或子任务一个统计层级。只有新需求形成独立交付目标时才另建任务。

同一上传者的 `task.id` 应跨窗口稳定保存。进行中或费用范围为部分的历史，不排除唯一的完整最终结算，也不把此前费用再叠加到最终结算。可选 `settlement-revision-1` 明确替代同一账期、全部根目标及原要求的整个快照；旧40、新100的当前费用为100，所有历史正文和反馈保留。没有明确替代的多份完整结算仍无法判定累计或增量，涉及的整条记录停止比较，不能只挑最近或成功的一份。关系判断先于证据、月份、模型和 Harness 筛选；私人新版也抑制公开祖先，相交根的未知链保留未知。字段及显式本地准备见 [跨次结算修订](settlement-revision-design.md)。

**账期**是一笔付费或一组连续付款覆盖的范围。套餐费用只能出现一次。`period.id` 是本地稳定保存的随机 UUID，真实账单编号及其映射留在采集端。一个账期内的失败、放弃和未完成工作也必须保留。存在进行中任务时，整期只用于个人分析，不能只把其中已完成的部分放入公开榜单。

**工作单位**用于描述一项任务原计划包含多少内容，例如文档章节、图表或流程步骤。它不是任务数：一份包含多个章节的报告仍可是一项任务，只有全部必需条件通过才算完成。

**比较条件**包括领域、任务类别、规模、验收方法、运行设置、模型及服务商版本、Harness 版本、月份、币种、付款类别、分摊规则和证据等级。公开接口返回达到门槛的固定分组，不提供逐条公开查询。

## 2. 任务类别与验收

领域由任务类别确定，不允许客户端另填一个矛盾的领域。以下规则覆盖常见工作；尚未归类的工作可作为 `other_work` 保存到个人记录，待有明确类别和标准后再参与公开比较。

| 领域       | 任务类别                               | 固定工作单位 | 验收要点，具体清单留在本地                     |
| ---------- | -------------------------------------- | ------------ | ---------------------------------------------- |
| 软件开发   | 功能开发、问题修复、代码重构、测试编写 | 独立代码改动 | 目标行为、边界条件、回归结果、运行环境         |
| 软件开发   | 文档工作                               | 文档章节     | 接口描述准确、示例可复现、必要章节完整         |
| 软件开发   | 工具配置                               | 流程步骤     | 指定环境能安装、运行、检查并得到预期结果       |
| 写作与翻译 | 文章起草、文字编辑                     | 文档章节     | 目标读者、必需内容、结构、事实、格式与语气     |
| 写作与翻译 | 翻译与本地化                           | 文档章节     | 原意与术语、数字和专名、格式与目标语言用法     |
| 研究与检索 | 资料检索、事实与来源核对               | 来源或核对项 | 搜索范围、来源身份、时间范围、可追溯结论       |
| 研究与检索 | 研究综合                               | 文档章节     | 纳入和排除条件、证据对应关系、分歧与限制       |
| 数据处理   | 数据清理、数据分析                     | 数据集       | 字段规则、样本范围、计算正确性、异常与缺失处理 |
| 数据处理   | 数据可视化                             | 图表         | 数据对应、统计口径、比例坐标、标签与输出规格   |
| 设计与媒体 | 视觉设计、产品与交互设计               | 视觉成果     | 尺寸、内容、交互状态、品牌要求和可访问性       |
| 设计与媒体 | 音视频编辑                             | 媒体片段     | 内容顺序、同步、字幕、分辨率、时长与导出规格   |
| 办公与流程 | 办公文档                               | 文档章节     | 数值、版式、字段完整性、编辑和导出可用性       |
| 办公与流程 | 办公流程                               | 流程步骤     | 授权边界、输入输出、失败处理、实际流程结果     |
| 运营与支持 | 内容运营、项目与活动规划               | 交付成果     | 目标、材料完整性、渠道规格、预算与执行条件     |
| 运营与支持 | 支持与事务处理                         | 事务         | 问题覆盖、处理准确性、权限范围、必要交接       |
| 教学与学习 | 教学材料、学习辅导                     | 教学单元     | 学习目标、知识正确性、适用难度和练习反馈       |

`scope` 描述预计影响范围。软件任务保留 `component`（单组件）、`module`（多组件）、`service`（多服务）；其他任务使用 `single`（单一成果）、`collection`（关联成果）、`cross_system`（跨系统或跨流程）。不知道就填 `unknown`。`context` 区分已有材料或项目与新建材料或项目。

`acceptanceTotal` 是独立、必需的验收结果数，范围为 1–100；公开按 1、2–3、4+ 分组。不能用测试断言条数、引用条数或文件数扩大验收结果数。`acceptancePassed` 不能超过总数；`accepted` 要求全部必需条件通过并记录人工、自动或联合验收方式。自动检查通过不自动证明业务质量。

`requirementsLocked=true` 表示任务开始前已在本地保存目标、规模和验收清单。事后补录填 false，并另行分组。需求改变时保留原清单、变更时间和原因，不能删掉失败条件后宣称完成。服务端检查结构和计数；独立验证方核对本地版本记录及成果。

## 3. 脱敏工作量摘要

服务端不接收自由填写的任务原文。摘要由以下白名单字段生成，不包含业务、客户、账号、项目、仓库、路径、文档标题、提示词或原始成果。

| 字段                       | 可提交内容                                                     | 判断规则                                            |
| -------------------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| `kind`、`scope`、`context` | 固定类别与范围                                                 | 任务开始前确定                                      |
| `dependencies`             | 0、1、2+、未知                                                 | 外部系统类别数，不上传系统名称                      |
| `workload.unit`            | 任务类别对应的工作单位                                         | 不同类别不能借换单位直接合并                        |
| `workload.inputUnits`      | 0、1、2–5、6–20、21+、未知                                     | 去重后的输入材料份数；同一文档分块不增加份数        |
| `workload.outputUnits`     | 1、2–5、6–20、21+、未知                                        | 事先要求的工作单位数，不是最终生成数量              |
| `workload.constraintCount` | 0、1–3、4–7、8+、未知                                          | 独立约束类别数，例如格式、时限、兼容性、合规要求    |
| `workload.verification`    | 测试、清单、来源核对、数据核对、评分标准、流程实测、混合、未知 | 事先指定验证方法，人工或自动方式另记                |
| `workload.inputSize`       | 固定计量单位与区间                                             | 只发送区间，不发送准确规模或原材料                  |
| `changeSize`               | 可选代码变更区间                                               | 仅软件任务使用，非软件任务必须为 null，不作价值分数 |

“1 份材料”不能说明其大小，因此材料份数和材料规模同时记录。材料规模单位由任务类型固定，不允许为了进入低难度组更换单位。所有区间的下界不包含上一档上限，上界包含本档上限。

| 计量单位       | 适用任务                                           | small                 | medium                       | large                      | very_large            |
| -------------- | -------------------------------------------------- | --------------------- | ---------------------------- | -------------------------- | --------------------- |
| `source_lines` | 功能、修复、重构、测试、工具配置                   | 1–200 行              | 201–2,000 行                 | 2,001–20,000 行            | 20,000 行以上         |
| `characters`   | 文档、写作、翻译、研究、运营内容、支持、规划、教学 | 1–4,000 字符          | 4,001–40,000 字符            | 40,001–400,000 字符        | 400,000 字符以上      |
| `cells`        | 数据清理、分析、可视化                             | 1–1,000 单元格        | 1,001–100,000 单元格         | 100,001–10,000,000 单元格  | 10,000,000 单元格以上 |
| `pixels`       | 视觉与交互设计                                     | 大于 0，至 200 万像素 | 大于 200 万，至 2,000 万像素 | 大于 2,000 万，至 2 亿像素 | 2 亿像素以上          |
| `seconds`      | 音视频编辑                                         | 1–60 秒               | 61–600 秒                    | 601–3,600 秒               | 3,600 秒以上          |
| `items`        | 办公流程及尚未归类的工作                           | 1–20 条               | 21–200 条                    | 201–2,000 条               | 2,000 条以上          |

`none` 表示确认没有该类输入材料；`unknown` 表示没有记录。两者不能互换。旧记录省略 `workload` 或 `inputSize` 仍可解析，缺失条件单独分组，不补成最小规模。

本地计量规则：

- 代码只统计任务开始前相关范围内的有效源文件行，排除依赖目录、生成文件、空行和重复副本。代码行只表示阅读材料规模。
- 文字按 Unicode 字符统计正文，去除空白和重复副本；不把系统提示词、重复历史对话或生成结果当输入材料扩充规模。
- 数据单元格按相关数据范围的行数乘字段数计算，多个数据集去重后求和；嵌套数据按参与处理的标量字段计数。记录清理前规模。
- 图像按实际提供的栅格材料宽乘高求和，同一图不重复计算。矢量设计无法按固定方式计量时填 unknown，不自行估一个像素数。
- 音视频按源媒体时长去重求和，秒数向上取整。多个处理阶段不重复累计同一片段。
- 流程条目是任务开始时要处理的单据、事件或事务数，不是工具调用次数。

这些字段控制已观察到的工作差异，不能完整描述任务难度。不同题材、目标质量、语言或领域知识仍会影响结果。需要复现实验时，在本地使用同一材料、同一验收清单和同一运行条件，由独立执行方核对；不能把粗分组当作完全相同的试题。

摘要例子：

- **软件修复**：已有项目／多组件／2–3 项验收／2–5 个独立改动／2–5 份材料／201–2,000 行输入／1–3 项附加约束／自动与人工核查。
- **文字编辑**：已有材料／关联成果／2–3 项验收／2–5 个章节／1 份材料／4,001–40,000 字符／评分标准与交付清单。
- **数据分析**：已有材料／单一成果／2–3 项验收／1 个数据集／100,001–10,000,000 单元格／数据核对。
- **视频编辑**：已有材料／关联成果／2–3 项验收／2–5 个片段／601–3,600 秒源媒体／人工按评分标准验收。
- **办公流程**：已有材料／跨系统／2–3 项验收／2–5 个步骤／21–200 条待处理事务／流程实测。

公开摘要还须得到单独同意，并在参与摘要的来源中重新满足发布门槛。不得直接从某一人的任务卡取详细计数或原文作为公共例子。

## 4. 成本与分摊

### 完成量与任务组成

当前 `evaluation` 保存已知计划组成、是否需要整合验收、实际完成/验收量、执行计数与资源用量。`completedWork` 按 kind、workType、unit 记录 planned/completed/accepted 及 source、acceptance、coverage。细分类目录和单位见 `/api/work-taxonomy`；未知细类可为 unknown，未测量数量为 null。不同单位分别汇总，源文字符数、最终交付字符数与 Token 不相互代替。原始目标和计数来源留在本地。

难度方案见 [分领域评价体系草案](difficulty-framework.md)。当前不采集主观难度字段，不运行评分或分级，不按旧 evaluation.profile 分层，排名接口不接受 difficulty 筛选。历史 work-1 的原始要求依据、主观分类、环境与置信度保持原样，当前摘要只读取其工作量和执行事实。不存在跨领域通用难度分或调整后的成本。

一个共同验收目标的多个部分只贡献一个根任务。独立验收的多个目标才能拆开，拆开后材料与费用不得重复归属。保存 `partsCompleted`、`partsAccepted`、`integrationAccepted`；已知部分未完成或整合失败时不得把根目标标为 accepted。

### 实付与补充费用信息

金额使用整数最小货币单位：人民币分、美元美分、欧元分。币种不同不相加，也不自动换汇。原始计费精度比“分”更细时，应先与整个账期实际账单对齐，不能独立舍入每次调用后假装金额守恒。

- 净实付为 `paidMinor - refundMinor`，退款不超过已付款。实付或退款未取得时使用 `null`，净实付也为 `null`；分摊方式必须是 `unallocated`，不能声明完整费用或进入成本排名。未知与确认零支出分别保存。
- API 逐任务实付合计不得超过净实付。差额保留为未归属费用；存在差额的整期不进入逐任务公开比较。
- 按 API 标价计算的金额放在 `apiEquivalentMinor`，必须带 `priceVersion`；它不等同用户付款。
- 旧记录的订阅及混合付费按照整期 Token 或任务数分摊。新记录可使用下述逐项费用归属，独有费用不进入共享池。分摊是会计估计，不代表某次请求单独付了这笔钱。
- 分摊采用 BigInt 整数最余数法，任务金额加未归属金额严格等于净实付。
- Token 总量缺失时不得按 Token 分摊。不完整订阅周期采用 `unallocated`，不从部分任务推算整期单价。
- 常规付款、促销、试用、赠送分组展示。套餐规则与分摊方式不同也分别比较。
- `costCoverage` 区分全执行费用、仅模型费用与未知；不同覆盖范围不合榜。`costComponents` 保留模型、Harness、工具、计算、存储、网络及其他净支出。全部分类已知时合计必须等于净实付，任何已知分类不得超过净实付。
- `billingBenefits` 记录取得的标价等价额、实际折扣、已用抵扣额、获赠与剩余额度、已含税费和平台费、额度到期时间、活动快照。它们是费用背景，不再累加到实付；未知为 null。未确认账户资格的宣传赠额不得作为实际获赠记录。
- 每项模型用量保留 `priceSnapshot` 和 `priceHistory` 的币种、实际抓取时间、已知生效时间、来源、单价与版本。没有历史快照就为 null，不用今日价格改写旧记录。跨币种 API 等价金额须带 `equivalentConversions` 的方向、汇率、日期与快照。

每项验收成本 = 本组全部任务费用 ÷ 通过验收的任务数。失败、部分完成、放弃的费用都在分子里；进行中任务所在账期暂不进入公开比较。零验收时单位成本为 null，保留支出与失败情况，不能把该分组从模型排名候选中删除。

### 逐项费用归属

`period.allocation=itemized` 配合 `period.costAttribution.version=cost-attribution-1`。这里的“直接归属”是一笔已经明确属于目标的净费用；“共享分摊”是一笔费用按明确规则分给指定目标；“未归属”是账期净额中尚未分给目标的部分。费用类型仍由 `costComponents` 记录，归属方式不等于费用类型，也不等于是否已独立核验。

`costAttribution` 含 `coverage=complete|partial` 及 `entries`。每行包含随机或本地加盐派生的 UUID `id`、整数 `netMinor` 和严格结构 `allocation`：

| method      | 字段                      | 含义                                                        |
| ----------- | ------------------------- | ----------------------------------------------------------- |
| direct      | taskId                    | 全额归属一个目标                                            |
| equal       | taskIds、unassignedWeight | 仅在指定目标与未归属份额之间均摊；每个目标权重为 1          |
| tokens      | taskIds、unassignedWeight | 仅按指定目标的输入加输出 Token 分摊；未归属权重使用相同单位 |
| unallocated | 无其他字段                | 本行金额全部保留为未归属                                    |

例如，A 的独有费用 40 元，共享费用 60 元在 A、B 间均分，结果为 A=70、B=30；不能把整笔 100 元均分。费用行均为退款后的净额，使用账期币种，不能再减一次账期退款或加入 API 等价金额。行净额合计不得超过账期净额；差额自动保留为未归属。负费用、跨期退款冲销及父子费用包含关系不由此协议推断。

完整明细须金额对齐并明确覆盖每个目标，已知零费用也要登记零金额直接归属；部分明细不因余额为零就变成完整。新模式下，旧 `directCostMinor` 和顶层 `unassignedWeight` 必须全部为 0；新明细不能与旧分摊模式同时出现。纯 API 只允许直接归属和未归属。共享分摊须有完整周期，按 Token 分摊只检查该行涉及目标的 Token；权重全零时金额保持未归属。

最多 500 行、累计 5000 个任务引用。费用行 ID 全表唯一，任务引用每行内部唯一且必须存在，允许一项目标参与多个费用池。同规则、相同目标集合及相同未归属权重的费用先合并再用 BigInt 最余数法分配，避免拆行改变舍入。余数相同时按稳定任务 UUID 排序，未归属份额排在目标之后；重排数组不影响结果，重新生成任务 UUID 可能改变不足一分钱的精确份额最终分给谁，不能借此创建重复付款。

该结构证明数值与引用一致，不证明费用行在经济意义上互不重叠。原账单 ID、账号、支付方式、账单正文及对应关系留在本地。签名摘要覆盖完整归属声明；同付款去重指纹不纳入归属声明，修改分摊或重编 UUID 不能被当成新付款。旧历史和冻结反馈不重写。

混合模型只计算一次任务完成。整个模型组合是一个比较对象，不按 Token 份额给不同模型分别分配“完成了一项任务”。

## 5. 用量、事件与时间

`inputTokens` 包含缓存读取和写入，`cachedInputTokens` 是已知缓存读取部分；`outputTokens` 包含已报告的思考量，`reasoningTokens` 是其中已知部分。总 Token 只加输入与输出。四项均可为 null；未知输入、输出、缓存或思考量不能自动写成 0。没有 Token 计数的图像、音视频或工作流任务，仍可记录实际付款和验收结果。

SDK 按提供商字段语义归一化。如果原接口缺少组成总量所必需的字段，则总量保持 null；如果服务商明确说明某字段缺省代表零，适配器应先在本地按该接口文档确定零值，再调用标准化函数。不能用文本长度猜账单 Token。

过程事件包括需求理解、软件实现、事实与来源、数据计算、格式与风格、隐私和素材条件、验收、工具环境、服务、会话调度及人工决策。当前 40 类事件见 `eventLabels`，`other` 接收其余已确认事件，后续按版本扩展。

返工指同一验收目标未达标后重做；修改指调整已有成果的一轮处理；重试指首次尝试后的再次执行。三者可以重叠，不能直接相加成总失败。每个事件单独记录次数和归因：模型、Harness、服务商、环境、用户、未知。发生事实和归因分别判断。

`events:null` 表示未采集；`events:[]` 表示检查后没有已知事件。返工、修改、人工投入等未记录时保持 null。同类事件合并为一个计数，不能重复列出。用户明确修改需求属于需求变更，不自动计为模型误解。

时间定义：

- `wallMs`：任务开始到结束的经过时间，包含等待与中断。
- `modelWallMs`、`toolWallMs`、`queueMs`：累计模型请求、工具执行和排队时间。并行时可以大于任务经过时间，不能相加当总耗时。
- `humanMinutes`：人工澄清、检查、修改与接管的主动投入；未计时则为 null。
- 首字延迟：`ΣttftSumMs / ΣttftSamples`。
- 可见输出速度：`Σ实测可见输出 Token / Σ对应输出阶段毫秒 × 1000`，不含首字前等待、工具等待和隐藏思考阶段。

公开比较中的每项可选测量单独要求至少 20 项观测、5 个来源、单一来源不超过 35%。不能依靠一个人数充足的大组，公布只有某一个人填写的时间或事件数据。

## 6. 排名规则

固定 Harness 可以比较不同模型；固定模型可以比较不同 Harness。完整条件保留在每一行，版本或材料规模不同不直接合并。

总体模型排名在同一领域、月份、原币、付费方式、付款类别、分摊规则、费用覆盖、评价版本及证据等级下计算。已发布固定目标的范围使用目标月份；未配置时明确标为临时共同范围，并自动选最新有数据月份。先确认属于单模型且 Harness 可归属，再选月份。新月份只有混合模型记录不能挤掉上月可用单模型数据。零验收记录仍参与月份选择和共同条件确定。

1. 已发布目标使用不可变条件和权重；未配置时先取候选模型共同覆盖的已观察条件，包括工作类型、范围、计划规模、验收要求及运行配置。旧主观难度向量和实际完成量不参与分组。先确定共同范围，再选择 Harness，不能先删除失败条件。当前摘要不能证明不同任务的复杂程度相同。
2. 对每个模型、每种任务条件、每个 Harness 及配置计算 `C = 本组全部实付 / 验收根任务数`。费用包含失败、放弃、重试和所有后代代理。验收数为零时 C 为 null，保留该候选与失败记录。
3. 每种条件单独选择该模型观察到 C 最低的 Harness/版本/配置/套餐。不同工作可以选择不同 Harness，不要求同一个 Harness 覆盖全部工作。费用相同时依次比较完成率、来源数、任务数与稳定配置标识，不设完成率门槛。
4. 领域总结果先对任务类型等权，再对类型内部的条件等权，得到权重 q。主成本为 `Σ(q × 每次发起支出) / Σ(q × 验收率)`；各条件单位验收成本的加权平均是另一种验收成果构成对照值，不是主成本。任务分类多寡不会让某一类型获得更多权重。任一目标条件缺失或没有验收成功，该模型总体成本为 null；不能跳过条件或重新分配权重。目标版本、覆盖及管理员发布方法见 [榜单目标版本](ranking-targets.md)。

按 C 升序排列；“每单位费用验收数”是其倒数，C=0 时只标为零实付，不生成无穷大分数。完成率为 `验收数 / 全部任务数`，只作解释指标，不分档、不筛选，也不再乘进性价比造成双重惩罚。例如总共付 100 元、通过 5 项，成本为 20 元/项；总共付 100 元、通过 10 项，成本为 10 元/项，无须先要求两者完成率相同。

每个条件返回选中的完整 Harness 配置、成本、完成率、任务数、来源数和所有候选。总体只有一种完整配置时才给 `selectedHarness`；多种配置通过 `selections` 和 `harnesses` 逐项显示。总体结果表示按工作选择 Harness 的观察组合，不是一份实际执行或多套餐采购报价。搜索名称只改变可见行，不能暗中重算共同工作范围。

混合模型任务保留整个模型组合，仅记一次根任务验收，不进入单模型榜。未知 Harness 或混合 Harness 同样不能冒充某个具体 Harness 的成绩。样本量、来源数、候选数和来源间成本范围随结果展示。范围是观察分布，不是置信区间；最低观察值存在选择偏差，不能称为未来价格或效果保证。

时间排名使用“本组全部任务经过时间 ÷ 验收任务数”；人工时间同理，均包含失败投入。返工、修改、意图误解按每次任务平均。总排名里的这些指标需覆盖全部共同条件且各条件全部任务有对应测量，否则为空。输出速度在每个条件内按输出阶段时长加权，再用相同条件权重合成。

费用榜附带的时间、人工、轮次、模型调用与代理数，都取同一个费用获选配置。不能从贵配置拿成功率、从便宜配置拿费用、从快速配置拿时间，拼成一项没有发生过的成绩。

套餐排名以套餐版本及所用模型组合为候选，采用相同工作条件与相同证据类别。不同币种、月份、分摊规则和领域不能合榜。完整周期的费用、验收任务数和人工投入保留，不能按用户希望完成的任务数拆开套餐付款。

## 7. 额度与建议

只有固定窗口、无重置、无其他账号活动且精确计量的额度记录，才具备换算每 1% Token 或 API 等价金额的条件。公开额度还要求验证方单独核对额度并给出 Q2；费用或工作签名不会自动获得额度核验资格。

每份额度观察必须属于提交记录的范围。已知的 Token 或 API 等价总量不能超过整份记录。每期最多附一份本地归并后的观察；采集端先处理窗口重叠、重复快照与恢复量。滚动额度不能简单用两次百分比相减。

额度发布的来源须单独满足至少 5 个来源及 35% 集中度要求。窗口长度、套餐版本、模型、输入规模、工作条件和核验类别相同才比较；环比只计算相邻月份，缺月不跨越。API 等价金额变化还要求两期使用同一价格快照。Token 比值变化只说明该条件下的观察变化，不能直接归因于供应商减少套餐总额度。

API 推荐以单位验收成本估计目标工作量对应的费用，并展示来源间观察范围。人工时间上限按每项验收任务计算，包含失败投入。缺少人工计时不能被当成满足零人工要求。

套餐推荐使用完整周期的已观察结果：周期验收任务数的第 25 百分位不低于目标工作量，已观察周期支出上限在预算内，每项验收人工投入满足要求。完成率不再是筛选门槛。它不按额度百分比推算无限产能，也不保证未来产出。

## 8. 全部层级代理、资源和历史

本地采集包保存 agents、events、charges、resources 与来源清单。树遍历不设置固定代理层数；每项事实用稳定本地 ID 去重，重复 ID 内容冲突时拒绝编译。旧费用采集及资源采集将累计值标为 aggregate，只汇总 direct 项；费用另可显式提供 [charge-coverage-1 包含关系](charge-reconciliation.md)，由程序核对累计总额、下界、未细分差额和任务归属。包含关系独立于代理树，不自动推断。原始 ID、父子边、提示词、业务原文、路径和账单不进入上传文件；来源用随机 salt 加盐生成摘要，salt 留在本地。

事件逐类声明完整性，分别记录真人轮次、助手回复、模型请求、工具调用及失败、上下文重置或压缩、人工介入、需求变更、路由切换、代理总数、最大深度和峰值并行。资源逐类声明完整性，汇总 CPU/GPU 秒、内存 GiB 小时、存储 GiB 天、网络字节、搜索、外部 API、图像与媒体秒。没观察到不是零；完整核对后确认没发生才能填零。

调用缺失可能隐藏其他模型，代理或生命周期费用不完整的整期只进入个人分析。资源汇总不完整的指标为 null。事件和资源每一项公开测量都独立满足发布门槛；详细私人字段不能借整个大组的人数直接公开。

原始贡献保持不可变，保留其价格版本和评价规则。公开目录、官方公告、AA 与汇率的变化追加到历史表，包括价格恢复为更早数值的情况。抓取时间不等同生效时间；仅保存实际观察到的快照，不补造开始采集前的历史。

趋势保持版本、任务条件、材料规模、证据类别一致。缺少月份时断开，不能插值制造改善。个人账期可以按月份及币种汇总；个人合计不等于严格条件下的模型排名。

## 按历史价格段保存计量数量

`Usage.cacheWriteTokens` 是可选的缓存写入数量；`inputTokens` 包含普通输入、缓存读取和缓存写入，三者互斥。`cachedInputTokens` 仅表示读取。`outputTokens` 已包含 `reasoningTokens`，推理附加费单独计价，不再增加总 Token。旧记录没有写入数量时保留未知。

可选字段 `priceMetering` 使用 `price-metering-1`：

- `coverage` 为 `complete` 或 `partial`，只针对本条模型用量的计量范围，不代表全部代理、工具、收费项目或完整账期。
- `segments` 最多 128 段。每段以 `snapshotId` 引用已保存的价格快照；跨币种同时通过 `conversionSnapshotId` 引用方向明确的历史汇率。
- `meters` 最多 12 项，每项为 `unit` 与 `quantity`。同段单位唯一，同价格加同汇率的段必须先合并。
- Token 费率按百万计价，但数量填原始整数 Token。其他单位直接填该费率的单位数量，例如 `second` 填秒、`compute_minute` 填分钟、`network_gib` 填 GiB。不是把所有时间都转换成秒。
- 四个桶 `input_million_tokens`、`cached_input_million_tokens`、`cache_write_million_tokens`、`output_million_tokens` 分别记录普通输入、缓存读、缓存写和输出，零也须明确。缺失不能填零。
- 每段存在正推理附加费时必须记录推理数量；明确零附加费可省略未知推理数量。已记录推理不能超过段内输出，也不能超过已知的整体推理数量；所有段均记录推理时须与整体一致。
- 价格表含图片、请求、搜索、时长等费率时，必须同时有对应数量（可以为零）。这些非 Token 数量目前没有独立总表对账，完整声明不构成独立真实性证明。

程序按 `Σ(数量 × 费率 ÷ 单位除数 × 该段历史汇率)` 计算；Token 单位除数为 1,000,000，其他单位为 1。同一模型的各段全部相加后，按非负数四舍五入到最小货币单位，当前三种币种均为分。使用保存后的 JSON 数值的十进制表示进行 BigInt 运算，不逐调用舍入，不使用当前汇率。上游已经损失的精度不能被恢复。合并数量不能被精确表示时拒绝合并；超过数量、金额或 128 段限制时要求缩小范围，不静默截断。

普通输入加读写缓存须对齐 `inputTokens`，读、写、输出另行对账。相同价格 ID 对应不同版本、币种、生效时间或费率，或同汇率 ID 对应不同方向、日期或汇率时，标记冲突；只有价格采集时间不同允许复用同价快照。哈希标识本身不证明价格来自服务商。

`apiEquivalentMinor` 继续保存来源报告金额，程序重算结果不覆盖它。新计量缺项、冲突、金额越界时不进入 API 等价统计；来源无报告金额但计量完整时可使用重算值，界面说明已完成重算，不声称已与来源对账。已有来源金额与重算不同则分别保留，差异可能来自源端舍入或数量、费率问题。旧记录没有 `priceMetering` 时沿用旧来源金额，并明确没有分段复核。多个模型各自舍入后的金额再汇总，不声称等同供应商整张账单的舍入结果。

本地采集先逐条检查再合并，单次冲突不能通过其他调用反向抵消；任何来源缺项都保持部分覆盖。额度窗口的等价金额仍为独立来源声明，不从周期总额按比例生成；存在新计量冲突时不发布该等价指标，若完整周期金额已知，窗口金额也不得超过周期总额。原声明、Token 和额度百分比继续保留。

这些金额均为历史 API 等价估计，不替代实际付款、订阅分摊、折扣、税费或退款。套餐和模型的实际成本主排名不改成 API 标价。不同缓存保留时长、阶梯价格等只有在已知对应费率与数量时才能通过明确价格段表达；不能从总 Token 反推。
