# 累计费用与子项核对

`charge-coverage-1` 是可选的本地包含关系协议，`charge-reconciliation-1` 是上传的数值摘要。它落实三份 Pro 资料关于父级累计、已知下界和费用归属分离的建议。原来的采集方式继续只加直接费用；新功能不自动启用，不扫描其他目录、不调用模型、不增加轮询。

## 三种不同的问题

| 问题         | 程序能核对的内容                                   | 不能据此推断的内容                                   |
| ------------ | -------------------------------------------------- | ---------------------------------------------------- |
| 总额是否重复 | 同一经济事件去重、明确包含与互斥关系、净额是否守恒 | 来源声明是否真实、是否遗漏未登记的外部费用           |
| 费用属于谁   | 明确任务归属、共享目标与分配规则、尚未归属的金额   | 父代理代付就等于父任务独有成本                       |
| 费用是什么   | 模型、Harness、工具、计算、存储、网络、其他类别    | 未分类金额属于 `other`，或代码修改多就应分配更多费用 |

包含图和代理树分开。一个代理可能代多个任务付款；一个账单可能跨多个代理。同一经济事件出现在两个日志里，应使用同一个本地费用 ID；不能因为日志来源不同而重复计费。没有供应商结算依据的 API 等价金额仍是等价金额，不写成实付。

## 本地输入

在现有采集包中添加 `chargeCoverage`，无需更改原有代理树：

```json
{
  "version": "charge-coverage-1",
  "periodId": "11111111-1111-4111-8111-111111111111",
  "basis": "collector_record",
  "rootsDisjoint": "declared",
  "relations": [
    {
      "parentId": "invoice-total",
      "childIds": ["model-call", "tool-charge"],
      "childrenDisjoint": "declared",
      "childrenCoverage": "partial"
    }
  ]
}
```

本例仅示意结构；`periodId` 必须引用本次真实账期。`parentId`、`childIds` 引用本地 `charges.id`，不出现在上传摘要。关联原件、账户、账单 ID、精确时间区间放在本地 manifest。调用方须先确定同一个费用覆盖期、币种和扣除关联退款后的口径；付款日期不能代替覆盖区间。程序校验本地账期 UUID、币种及净额，无法仅凭声明证明区间一致。

- `basis` 为 `collector_record`、`user_report` 或 `unknown`，描述关系依据，不提升证据等级。
- `rootsDisjoint` 声明各根费用范围是否互斥；`childrenDisjoint` 对同一父级的直接子范围作相同声明。
- `childrenCoverage=complete` 表示所列子范围完整覆盖父范围；子金额全已知且互斥时必须与父金额相等。`partial` 允许有尚未细分的金额。
- 启用此协议时，费用 `amountMinor` 可为 `null`，表示没有取得该节点金额；不能填零代替。`component` 可额外为 `mixed` 或 `unknown`，不能用 `other` 代替未知。
- 每个 `aggregate` 必须有一条 relation；没有子明细时使用空 `childIds` 和 `childrenCoverage=partial`。同一节点只能属于一个父级，不支持重叠包含的多父图。
- 节点上的 `allocation=direct` 是整个范围均归该任务的明确声明，会约束后代；aggregate 的 `taskId` 仅为本地上下文，不自动给差额分配任务。
- `remainderAllocation` 和 `remainderComponent` 只描述已知完整子金额之外的差额。可以直接归属，也可以在 mixed/subscription 的 itemized 模式明确共享规则。父级整体的均摊规则不能被解释为差额均摊。
- 新图使用 `period.allocation=itemized`、纯 API 的 `direct`，或明确的 `unallocated`。不能沿用旧整期 equal/tokens 把图中未归属金额自动均摊；转换需要明确的逐项规则。

## 计算规则与例子

使用整数最小货币单位和 BigInt 计算。先按本地稳定 ID 去重，再校验引用、单父关系与循环。自底向上得到每个范围的已知金额或下界；子范围互斥时加总，不知道是否互斥时只取最大下界。自顶向下输出互不重复的费用部分，不同时累计父总额和后代金额。

| 来源记录                                   | 程序结果                                                      |
| ------------------------------------------ | ------------------------------------------------------------- |
| 父 100，子 A 模型费 30、子 B 工具费 20     | 总额 100；已知 A30、B20；差额 50 尚未映射或分类               |
| 上例明确差额 50 由 A/B 均摊                | A55、B45；类别另行判断，不能因此认定 50 属于 Harness          |
| 父 100，A 独有 40，其余 60 明确由 A/B 均摊 | A70、B30；不把父 100 再加一遍                                 |
| 父 100，互斥子项 70、50                    | 冲突；不输出有效派生金额，也不生成上传文件                    |
| 父金额未知，子项 30、20                    | 已知下界 50；不能声明完整账期成本                             |
| 父 100，子 Q 金额未知，Q 下已知 30         | 总额 100，未细分 70；这 70 可能部分属于 Q，不能套父的差额规则 |
| 父 100，兄弟子项是否重叠未知               | 保留父 100，子项不再次加入；未能确认的任务和类别分解保持未知  |
| 两个根分别 60、50，是否重叠未知            | 下界 60，不相加成 110；不生成猜测的任务分摊                   |

未知子总额时，只有覆盖整个父范围的明确任务或类别声明能约束未细分金额。比如整个父范围都是模型费用，可以保留这一分类；仅声明父自己的剩余部分为模型费用，则不能推及未知子项。

总额只有在费用采集声明完整、根范围互斥、根金额均已知且合计等于账期净实付时标为 `reconciled`。未知父金额即使已有子项，也仅输出下界。`partial` 保留已知金额；`conflict` 所有派生金额为 null。未知和冲突均不填零。

## 已存归属与新采集明细

旧账单已明确 A40/B60，新图只确认子 A30/B20、另有未映射 50，两者可以同时成立。程序保留旧归属，只检查本次明确部分不超过对应旧金额；未映射差额不作为否定旧归属的一条新费用。只有本次总额和任务映射都完整时，才逐组作等额核对。

本次包含图仍有未映射金额时，即使旧明细已分配全部费用，也不将本次图当作完成归属复核，不进入单位成本、用户位置或推荐比较。私人反馈展示旧明细和本次缺项各自的含义。未知共享权重产生的最终未分配金额仍由原有分摊器单独计算。所有旧文件和冻结反馈保留原值，不重新解释旧历史。

## 上传与展示

只新增 `period.chargeReconciliation`：版本、状态、依据枚举、节点/关系/深度计数、已知总额、下界、账单尚未解释金额、未细分差额、本次图未映射金额、未分类金额、固定七类费用下界、未解决组数及固定诊断代码。不上传包含边、原始 ID、账户、路径、原文、精确时间、供应商账单原件或自由文本。

这些金额可重叠，不能相加。`componentLowerBounds` 是类别下界；`costComponents` 是总额类别，含义不同。分类缺项时不把下界当作类别总额，未知部分不记入 `other`。`unmappedMinor` 只描述本次图中未映射的部分，不等于最终账单的未分配金额。

网页与桌面使用同一个反馈面板；文本反馈保留相同解释。公共排名只使用原有聚合发布机制，不公开这份私人诊断。哈希绑定本地采集内容，不证明账单真实；关系声明也不能识别重新生成 ID 的同一经济事件。

## 使用方式与处理预算

```powershell
npm run contribute -- init --out capture.json --itemized-costs --charge-coverage
npm run contribute -- reconcile-charges --input capture.json --out NEW-diagnostic.json
npm run contribute -- capture --input capture.json --out record.json
```

先按现有首次说明选择范围，再依据授权来源填写模板。诊断只检查费用包含结构与金额，不代替完整采集编译、任务引用、账单真实性或上传预览校验。诊断文件必须使用新路径，冲突也可保存；原数据留在本地。以上命令不上传，后续 prepare、用户确认和 submit 沿用既有流程。

单包读取不超过 64 MiB；新图最多 100,000 条费用输入、200,000 条包含引用及 200,000 个任务归属引用。遍历使用显式队列，时间和中间状态随节点与引用数线性增加，不限制固定层数，也不为每个父节点复制全部后代。输出沿用最多 500 个归属组、5,000 个任务引用等限制；超限明确停止，不截掉费用。资源用量的 aggregate/direct 规则保持原状；本功能不解决跨期退款、跨期共享账单或多父重叠事件的结算。
